## Термины и четыре условия

Deadlock — взаимоблокировка: участники ждут друг друга и не могут продолжить.
Это отличается от долгой операции и от голодания, когда другие потоки продолжают
работать, а один не получает ресурс.

Четыре необходимых условия Коффмана:

1. Взаимное исключение: ресурс одновременно принадлежит одному участнику.
2. Удержание и ожидание: участник держит ресурс и ждёт ещё один.
3. Отсутствие принудительного изъятия: ресурс освобождает владелец.
4. Циклическое ожидание: цепочка ожиданий замыкается.

Для предотвращения достаточно исключить хотя бы одно условие.

## 1. Настоящий deadlock и его диагностика

Запустить:

```bash
python3 deadlock.py
```

Это намеренно неисправная программа. T1 берёт A, T2 берёт B. Барьер
гарантирует, что оба уже держат первую блокировку, прежде чем запрашивать вторую.
T1 ждёт B, T2 ждёт A. Спустя секунду `faulthandler` печатает стеки потоков,
но программа НЕ завершается: оба рабочих потока стоят на `with second`,
главный поток ждёт `join()`.
Вывод `Timeout` от faulthandler означает срок до печати стеков, а не автоматическое
прерывание заблокированной программы.

Удобный ограниченный запуск в WSL:

```bash
timeout 4s python3 deadlock.py --dump-after 1
echo $?
```

`timeout 4s` даёт программе 4 секунды и затем посылает SIGTERM.
Код 124 означает, что процесс пришлось остановить по тайм-ауту.
Неисправная программа сама из deadlock не выходит; ограничение находится снаружи.
Для сохранения стеков:

```bash
timeout 4s python3 deadlock.py --dump-after 1 > results/raw_manual.txt 2>&1
```

`>` сохраняет stdout; `2>&1` направляет stderr с диагностикой в тот же файл.
Если уже запустили без timeout и Ctrl+C не завершил процесс из-за ожидающих
потоков, откройте второй терминал, найдите PID через
`ps -u "$USER" -o pid,args | grep '[p]ython3 deadlock.py'`
и выполните `kill -TERM PID`, подставив найденный PID.

Сохранённый пример: [results/raw_deadlock.txt](results/raw_deadlock.txt).
Генератор наблюдает зависание 1,2 с, получает стеки и завершает только свой процесс.

### Исправление единым порядком

```bash
python3 deadlock.py --mode ordered
```

Оба потока теперь берут A, затем B. Ожидается:

```text
T1: finished
T2: finished
ORDERED: both threads finished
```

Порядок первых двух строк может отличаться. Барьер синхронизации старта
в этой версии расположен ДО захвата блокировок.
Единый порядок исключает циклическое ожидание: нельзя двигаться по строго
возрастающим номерам ресурсов и вернуться к исходному номеру.
Добавление `sleep` не является исправлением; оно не устраняет возможность цикла.

## 2. Алгоритм банкира

Входные `.txt` содержат JSON: `resources`, `available`, список процессов с
`allocation`, `max` и необязательный `scan_order`.

- Available — свободные экземпляры каждого типа ресурса.
- Allocation — уже выделенные ресурсы процесса.
- Max — максимальная заявленная потребность, включая уже выделенное.
- Need = Max − Allocation — сколько ещё может понадобиться.
- Work — временная копия Available при моделировании завершений.

### Контрольные состояния

```bash
python3 banker.py bank1.txt < /dev/null
python3 banker.py bank2.txt < /dev/null
```

`< /dev/null` сразу передаёт EOF, поэтому программа не ждёт интерактивных запросов.

Для bank1:

```text
Available: [3, 3, 2]
SAFE: P1 -> P3 -> P4 -> P2 -> P0
```

Для bank2:

```text
Available: [0, 1, 0]
UNSAFE
```

Матрица Need у обоих наборов:

| PID | A | B | C |
|---|---:|---:|---:|
| P0 | 7 | 4 | 3 |
| P1 | 1 | 2 | 2 |
| P2 | 6 | 0 | 0 |
| P3 | 0 | 1 | 1 |
| P4 | 4 | 3 | 1 |

Проверка указанной последовательности для bank1:

```text
начальный Work: [3, 3, 2]
после P1:       [5, 3, 2]
после P3:       [7, 4, 3]
после P4:       [7, 4, 5]
после P2:       [10, 4, 7]
после P0:       [10, 5, 7]
```

На каждом шаге Need выбранного процесса <= Work покомпонентно.
После его условного завершения прибавляется именно Allocation, а не Max и не Need.
Проверка не изменяет реальное распределение ресурсов.

Безопасных последовательностей может быть несколько. `scan_order` задаёт
порядок проверки кандидатов, чтобы вывести именно последовательность из задания.
Ответ не зашит в алгоритм: каждый шаг проверяется по Need и Work,
безопасность также проверена перебором всех последовательностей на малых таблицах.
Если поле убрать, используется порядок строк процессов в файле.

UNSAFE означает отсутствие гарантированной последовательности завершения
при максимальных заявках. Это не доказательство уже наступившего deadlock:
реальные будущие запросы могут оказаться меньше Max.

### Запросы из stdin

```bash
python3 banker.py bank1.txt
```

После начальной таблицы вводить команды и нажимать Enter:

```text
P1 1 0 2
show
safe
quit
```

Запрос P1 `(1,0,2)` выдаёт `GRANTED`.
После него Available = `[2,3,0]`, Allocation P1 = `[3,0,2]`, Need P1 = `[0,2,0]`.
Состояние остаётся безопасным.

Одной командой тот же эксперимент:

```bash
printf 'P1 1 0 2\nshow\nsafe\nquit\n' | python3 banker.py bank1.txt
```

`printf` формирует строки; `\n` — перевод строки; `|` направляет их в stdin банкира.
Каждый новый запуск заново читает исходную таблицу из файла.

### Проверка отката

На свежем bank1:

```bash
printf 'show\nP4 3 3 0\nshow\nquit\n' | python3 banker.py bank1.txt
```

Получится `DENIED_UNSAFE`, а таблицы до и после запроса будут одинаковыми.
Временная выдача оставляет Available `[0,0,2]`; никто не может гарантированно
завершиться. `finally` восстанавливает Available и Allocation, Need пересчитывается.

Другие варианты результата:

- `REJECTED` — запрос превышает оставшуюся заявленную Need.
- `WAIT` — запрос допустим по Need, но сейчас не хватает Available.
- `ERROR` — неизвестный PID, неверное число компонентов или отрицательные числа.

Инварианты проверяют неотрицательность ресурсов, Allocation <= Max и сохранение
общего количества каждого ресурса после выдачи и отката.
В этой работе моделируются выдачи; отдельная команда реального завершения
процесса не предусмотрена и для заданной функции `request` не требуется.

## 3. Граф ожидания по журналу

Формат строки:

```text
acquire T1 A
wait T1 B
release T1 A
```

Это обозначения отдельных событий, а не обязательная последовательность:
в модели заблокированный участник не может исполнять release, пока его ожидание
не закончилось. Файлы `events_*.txt` содержат полные допустимые сценарии.

Каждый ресурс имеет ровно один экземпляр; у участника одно текущее ожидание.
`acquire` означает успешный захват, `wait` — блокирующий запрос занятого ресурса,
`release` — освобождение владельцем.
Детектор проверяет согласованность событий.

```bash
python3 wait_graph.py events_deadlock.txt
python3 wait_graph.py events_safe.txt
```

Первый выводит:

```text
DEADLOCK at line 5: T1 -> T2 -> T1
Participants: T1, T2
```

Второй выводит `NO DEADLOCK`.
Вершины графа — только участники. Ребро `T1 -> T2` означает, что T1 ждёт
ресурс, который держит T2. Владельцы и ожидания хранятся раздельно,
граф пересобирается по текущему состоянию, поэтому устаревшие рёбра не остаются.

DFS использует белый/серый/чёрный цвет вершины; ребро в серую вершину
текущего стека означает цикл. Возвращается один найденный цикл и его участники.
Для нескольких экземпляров одного ресурса такой критерий применять напрямую нельзя.

## 4. TrackedLock в реальном времени

```bash
python3 deadlock.py --mode tracked
```

Ожидается сообщение `DEADLOCK: T1@... -> T2@... -> T1@...`
(начальная вершина может отличаться), затем успешное завершение другого потока:

```text
RECOVERED: exception released held locks through with; graph empty
```

Вместо зависания новый захват, который замкнул цикл, бросает `DeadlockDetected`.
Исключение выходит через `with`, поэтому уже удерживаемая этим потоком блокировка
освобождается. Второй поток получает возможность закончить работу.
Простого обнаружения цикла недостаточно для восстановления, если исключение
перехватить внутри критической секции и продолжать держать ресурс.

Внутри каждой обёртки есть настоящий `threading.Lock`. У всех обёрток общий
`LockTracker` с `Condition`. Обновление владельцев, ожиданий и DFS происходит
атомарно под мьютексом монитора. Занятый сырой lock проверяется неблокирующим
захватом; ожидание выполняется через Condition, освобождая мьютекс монитора.
Нельзя блокироваться на сыром lock, удерживая служебный мьютекс графа.

Поддержаны `with`, `acquire`, `release`, `locked`, неблокирующий захват и тайм-аут.
Это нерекурсивная блокировка; повторный блокирующий захват тем же потоком
образует цикл из одной вершины. Release проверяет владельца.
После отменённого захвата/тайм-аута запись ожидания удаляется.
Имена блокировок уникальны внутри одного tracker.

Ограничение: отслеживаются только обёрнутые блокировки одного общего tracker.
Deadlock на обычном Lock, вводе-выводе или других внешних ресурсах такой
детектор не видит. Он также не гарантирует отсутствие голодания.

## 5. Обедающие философы

```bash
python3 philosophers.py --seconds 2
```

Запускаются три отдельных процесса эксперимента, по 2 секунды наблюдения:

1. `naive`: каждый берёт левую вилку и ждёт правую. Барьер после первого
   захвата гарантирует цикл: все пять держат по вилке и ждут соседнюю.
2. `ordered`: сначала вилка с меньшим номером, затем с большим.
3. `waiter`: семафор допускает к попытке захвата не более четырёх философов;
   вилки берутся в исходном порядке «левая, правая».

В таблице показывается, сколько раз поел каждый философ.
У naive все счётчики равны 0, а пять потоков остаются заблокированными.
Это не «успешное завершение потоков»: снимок делает главный поток отдельного
процесса. Рабочие потоки намеренно daemon, и при выходе процесса они исчезают.
Настоящая не завершающаяся программа также отдельно приложена в `deadlock.py`.

В corrected-вариантах после интервала наблюдения выставляется stop,
потоки заканчивают текущую итерацию, освобождают вилки и завершаются через join.
Поэтому фактическая длительность может немного превышать заданные 2 секунды.

Результаты: [results/table.md](results/table.md), сырые данные:
[results/philosophers.json](results/philosophers.json).
Точные счётчики зависят от планировщика и могут меняться при повторном запуске.
Положительные счётчики подтверждают прогресс в данном эксперименте,
но не доказывают справедливость и отсутствие голодания при любом расписании.
В JSON `max_wait_seconds` относится к ожиданиям, закончившимся приёмом пищи;
у naive завершённых ожиданий нет, нули не означают отсутствия ожидания.

Нумерация вилок исключает циклическое ожидание. Ограничение N−1 не позволяет
всем пяти одновременно удерживать по левой вилке; хотя бы один допущенный
может получить вторую и освободить ресурсы. Длительности thinking/eating
используются для нагрузки, а не как исправление синхронизации.

## Контрольные вопросы

**1. Почему упорядочивание захвата ресурсов исключает deadlock?**

Все участники запрашивают ресурсы в одном строгом порядке. В цепочке ожидания
каждый следующий запрашиваемый ресурс имеет больший номер. Чтобы получился
цикл, пришлось бы вернуться к меньшему номеру, что запрещено.
Тем самым нарушается условие циклического ожидания. Важно соблюдать порядок
во всех участках программы и не вводить другие циклы на внешних ресурсах.

**2. Почему алгоритм банкира редко используется в универсальных ОС?**

Нужно заранее знать максимальную потребность каждого процесса в каждом типе
ресурсов. Для произвольных программ это обычно неизвестно; процессы и ресурсы
динамически появляются и исчезают. Проверка каждого запроса стоит времени,
а консервативное удержание системы в безопасном состоянии может уменьшать
использование ресурсов. Поэтому алгоритм удобен прежде всего для моделей
и систем с заранее известными ограничениями, а не как общий механизм ОС.
