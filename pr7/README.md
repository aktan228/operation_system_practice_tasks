# Практическая работа № 7. Межпроцессное взаимодействие

Вариант B. Python 3.8+, Linux/WSL2, только стандартная библиотека.

## Что реализовано

1. Арифметический сервис на двух FIFO: общий канал запросов и общий канал ответов.
   Клиенты обслуживаются последовательно; `flock` защищает полный запрос/ответ.
2. Тот же сервис на Unix domain sockets (`AF_UNIX`, `SOCK_STREAM`).
   Несколько клиентов работают одновременно, сервер создаёт отдельный процесс
   через `multiprocessing` с методом `spawn` на каждое соединение.
3. Передача массива 10^7 целых uint32 (40 000 000 байт, около 38,15 MiB)
   от родительского процесса дочернему через `shared_memory` и `Pipe`.
4. Сверка SHA256 всех байт, повторные замеры, таблица и проверки очистки.

| Файл | Назначение |
|---|---|
| `calculator.py` | Разбор арифметики через AST, без `eval` |
| `ipc_common.py` | JSON-протокол и обработчики сигналов |
| `fifo_service.py` | Сервер и клиент на FIFO |
| `unix_service.py` | Сервер и клиент на Unix-сокетах |
| `bench_memory.py` | Сравнение shared memory и Pipe |
| `run_experiments.py` | Полный эксперимент и генерация таблицы |
| `test_ipc.py` | Автоматические проверки |
| `results/` | Реальные измерения в WSL и вывод тестов |

## FIFO: два терминала

FIFO — именованный канал: путь есть в файловой системе, данные передаются
через буфер ядра, а не сохраняются в обычном файле. Это поток байт в одном направлении.
Для двустороннего сервиса используются два FIFO.

### Терминал 1: сервер

```bash
cd ~/repo-for-practice3/pr7
python3 fifo_service.py server
```

Ожидается строка вида:

```text
READY FIFO directory=/tmp/pr7-fifo-1000 pid=1234
```

UID и PID могут отличаться. Сервер остаётся работать и ждать запросы — это нормально.
Не закрывать этот терминал до окончания демонстрации.

### Терминал 2: клиенты

В Windows Terminal открыть ещё вкладку Ubuntu через кнопку `+` или меню рядом
с ней. Если открылась вкладка PowerShell, выполнить `wsl -d Ubuntu`.

```bash
cd ~/repo-for-practice3/pr7
python3 fifo_service.py client '2 + 3 * 4'
python3 fifo_service.py client '(10 - 2) / 4'
python3 fifo_service.py client '2 ** 10'
python3 fifo_service.py client '1 / 0'
```

В JSON-ответах: `result` равен 14, 2.0 и 1024 соответственно.
Для деления на ноль возвращается `"ok": false` и описание ошибки;
сервер продолжает обслуживать другие запросы.
Каждый запуск клиента — новый процесс, его PID указан в `client_pid`.
`seconds` — длительность обмена запрос/ответ, `wire_bytes` — объём JSON-запроса
и ответа с переводами строк. Это не размер служебных структур ядра.

Кавычки нужны, чтобы оболочка передала выражение как один аргумент
и не интерпретировала `*`, скобки и пробелы.

### Остановка и проверка

В терминале 1 нажать Ctrl+C. Ожидается:

```text
CLEAN FIFO
```

Сервер закрывает дескриптор и удаляет оба FIFO, файл блокировки и каталог.
Проверить в терминале 2:

```bash
test ! -e /tmp/pr7-fifo-$(id -u) && echo 'FIFO cleanup OK'
```

`id -u` возвращает UID; `$()` подставляет результат команды.
`test ! -e` проверяет отсутствие пути; `&&` запускает следующую команду при успехе.

## Unix-сокеты: два терминала и одновременные клиенты

Unix-сокет — локальный двусторонний канал с адресом-путём.
Сетевой IP-адрес и порт здесь не используются.

Терминал 1:

```bash
cd ~/repo-for-practice3/pr7
python3 unix_service.py server
```

Ожидается `READY UNIX ...`.

Терминал 2:

```bash
cd ~/repo-for-practice3/pr7
python3 unix_service.py client '6 * 7'
```

В ответе `result` равен 42. `worker_pid` — PID дочернего процесса сервера,
который обслужил именно это соединение.

Для пяти одновременных клиентов выполнить блок целиком:

```bash
for expression in '2+2' '3*7' '10/2' '2**8' '(9-1)*3'; do
    python3 unix_service.py client "$expression" &
done
wait
```

`&` запускает команду в фоне, не ожидая её окончания. `wait` ждёт завершения
всех фоновых клиентов этого терминала. Результаты появятся в произвольном порядке:
4, 21, 5.0, 256, 24. У ответов будут разные `worker_pid`.
Сервер не ждёт завершения предыдущего клиента перед приёмом следующего.

Остановить сервер Ctrl+C. Ожидается `CLEAN UNIX`.

```bash
test ! -e /tmp/pr7-unix-$(id -u) && echo 'Unix socket cleanup OK'
```

Для остановки через сигнал вместо Ctrl+C можно использовать в другом терминале
`kill -TERM PID`, подставив PID из строки READY. Обрабатываются SIGINT и SIGTERM.

## Протокол и синхронизация сервиса

Запрос — JSON-объект с уникальным `id` и строкой `expression`, завершённый `\n`.
Ответ содержит тот же ID, `ok` и `result` либо `error`.
Поддержаны числа, скобки, `+ - * / // % **` и унарные знаки.
Вызовы функций, доступ к атрибутам, переменные и выполнение кода не разрешены.
Ограничены длина выражения, глубина/размер дерева, степень и величина результата.

Для FIFO одной атомарности короткой записи недостаточно: другой клиент может
прочитать чужой ответ из общего FIFO. Поэтому межпроцессная `flock` удерживается
на всём обмене, а не только на записи запроса. Записи укладываются в `PIPE_BUF`.
Клиент открывает канал ответов до отправки запроса; ожидания имеют тайм-аут.
Сервер на Linux открывает FIFO запросов с `O_RDWR|O_NONBLOCK`, чтобы запуск
не блокировался до первого клиента. Это Linux-приём, а не переносимая POSIX-гарантия.

У сокетов отдельное соединение на клиента, поэтому ответы не смешиваются.
Однако `SOCK_STREAM` не сохраняет границы сообщений: один `recv` может прочитать
только часть JSON. `read_line` накапливает байты до `\n`, `sendall` отправляет весь ответ.
Одна сессия обслуживает один запрос, затем соединение закрывается.

## Массив из 10 миллионов чисел

Запустить в одном терминале; оба сервера при этом могут быть остановлены:

```bash
cd ~/repo-for-practice3/pr7
python3 bench_memory.py
```

По умолчанию передаются числа 0..9 999 999 в `array('I')`, 4 байта на число.
Это 40 MB в десятичном счёте, а не список из 10 миллионов Python-объектов.
Производитель — родительский процесс, получатель — отдельный дочерний процесс.

Для shared memory создатель выделяет сегмент, получатель подключается по имени.
После сигнала готовности получателя начинается замер: родитель копирует исходные
данные в сегмент и устанавливает `multiprocessing.Event`. Получатель не читает
данные до `Event.wait()`. После публикации родитель не изменяет сегмент.
Затем получатель подтверждает доступность и проверяет SHA256 всех байт.

Для Pipe передаются те же байты через `send_bytes`/`recv_bytes`, без pickle массива.
Используется отдельный однонаправленный канал данных и канал подтверждений.
Неиспользуемые концы закрываются; получатель читает одно сообщение заданного
протокола, а не ждёт EOF при открытом пишущем конце.

Ожидается таблица двух механизмов, `SHA256: OK; cleanup: OK`.
Замеры повторяются трижды, порядок механизмов чередуется, выводится медиана.

### Что именно измеряется

- `handoff_seconds`: от начала копирования в shared memory или отправки в Pipe
  до получения подтверждения, что данные доступны получателю.
- `verified_seconds`: от того же начала до подтверждения полной SHA256-проверки.

Подготовка исходного массива, создание процессов/сегмента и подключение
получателя к сегменту исключены. Для shared memory копирование из исходного
массива ВКЛЮЧЕНО. Заполнение страниц сегмента впервые может требовать работы
ядра даже после создания объекта сегмента.
Это сравнение двух конкретных протоколов, а не «времени передачи имени сегмента».
Первое подтверждение shared memory ещё не означает чтение всех 40 MB;
поэтому отдельно приводится время с полной проверкой для обоих механизмов.

Небольшой пробный запуск:

```bash
python3 bench_memory.py --count 100000 --repeats 1 --out results/small_memory.json
```

Для сдачи использовать именно значение по умолчанию 10 000 000.

## Полный эксперимент и таблица

```bash
python3 run_experiments.py
```

Программа сама запускает временные серверы, 10 отдельных FIFO-клиентов
последовательно, 10 Unix-клиентов одновременно и передачу большого массива.
После эксперимента останавливает серверы и проверяет удаление ресурсов.
Результаты сохраняются в:

- `results/table.md` — таблица «механизм — синхронизация — объём — время»;
- `results/services.json` — отдельные ответы, PID и времена запросов;
- `results/memory.json` — все замеры, SHA256 и имена удалённых сегментов.

Таблица с реальными измерениями WSL: [results/table.md](results/table.md).
Просмотр в терминале: `cat results/table.md` или `less results/table.md` (выход — q).
Открыть папку в Проводнике Windows: `explorer.exe .`.

Маленький арифметический RPC нельзя напрямую сравнивать с передачей 40 MB.
Сокеты здесь дополнительно оплачивают запуск процесса на каждый запрос;
при конкурентном запуске клиенты делят CPU. Поэтому большее время сокетного
запроса не означает, что FIFO универсально быстрее сокета.
Аналогично shared memory не обязана выигрывать в каждом замере:
в данном протоколе нужно сначала скопировать массив в новый сегмент и
синхронизировать процессы. Pipe может оказаться быстрее на этой машине.
Преимущество shared memory особенно заметно при повторном доступе к уже
общим данным, когда их не требуется снова передавать или копировать.

## Тесты и очистка

```bash
python3 test_ipc.py
```

Ожидается `Ran 7 tests ... OK`. Проверяются арифметика и ошибки,
FIFO с конкурирующими вызывающими потоками, отдельные процессы обработчиков
сокетов, частичная доставка сообщения, остановка по SIGINT,
SHA256 массива и удаление сегментов. SIGTERM используется при завершении
серверов тестами и полным экспериментом.

Сохранить свой вывод:

```bash
mkdir -p results
python3 test_ipc.py > results/tests.txt 2>&1
python3 run_experiments.py > results/experiment.txt
cat results/tests.txt
cat results/table.md
```

Не запускать Python с `-O`, чтобы не отключать `assert`.
Полный эксперимент проверен в Ubuntu WSL2 с Python 3.14.4.

Проверка после остановки ручных серверов и завершения экспериментов:

```bash
find /tmp -maxdepth 1 -name 'pr7-*' -print
ls -la /dev/shm
```

Первая команда не должна находить каталоги этой работы. В `/dev/shm` не должны
оставаться созданные работой сегменты; чужие объекты удалять не нужно.
В сохранённом проверочном запуске `/dev/shm` был пуст после завершения.
Проверка каждого конкретного сегмента также выполняется программно:
повторное открытие после `unlink()` должно дать `FileNotFoundError`.

Получатель вызывает `close()`, создатель — `close()` и `unlink()` в `finally`.
Сервер удаляет только файлы в собственном новом каталоге. Если каталог уже есть,
новый сервер отказывается его перезаписывать. Можно использовать другой
`--directory /tmp/pr7-my-run`, одинаковый у клиента и сервера.
SIGKILL и отключение питания не позволяют выполнить `finally`: гарантия очистки
относится к штатному завершению, обработанным SIGINT/SIGTERM и исключениям.
Очереди сообщений в варианте B не создаются.

## Ответы на контрольные вопросы

**1. Почему shared memory называют самым быстрым и опасным IPC?**

Процессы могут обращаться к одним физическим страницам, поэтому не нужно
копировать весь массив через ядро при каждом обмене. Но механизм сам не задаёт,
когда данные готовы и кто может их изменять. Без Event, семафора, мьютекса или
другого корректного протокола возможны гонки и чтение частично записанных данных.
Нужно согласовать формат, размер и время жизни сегмента. «Самый быстрый» —
упрощение: создание, первое заполнение и синхронизация тоже имеют стоимость.

**2. Что произойдёт при записи в pipe без читающих концов?**

На Unix возникает SIGPIPE. При обработке сигнала по умолчанию процесс завершается;
если сигнал игнорируется или обрабатывается, запись возвращает ошибку EPIPE.
Python обычно игнорирует SIGPIPE и сообщает `BrokenPipeError`.
Это отличается от открытия FIFO на запись: блокирующий `open` ждёт читателя,
а неблокирующий `open` при его отсутствии выдаёт ENXIO.
