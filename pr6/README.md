# Практическая работа № 6. Синхронизация — вариант B

## Цель и состав работы

Реализованы без `queue.Queue`:

1. Кольцевой буфер на 5 элементов: два семафора и мьютекс.
2. Такой же буфер: мьютекс и одна условная переменная.
3. Три производителя и два потребителя, 1000 элементов суммарно.
4. Контроль уникальности, полноты обработки и границ буфера.
5. Многоразовый барьер на условной переменной для 4 потоков и 3 фаз.
6. Ошибка `if` вместо `while`, настоящее потерянное уведомление и исправления.

Python 3.8+. Сторонних библиотек не требуется.
Запускать обычным `python3`, без `-O`: этот ключ отключает `assert`.

## Термины

- Поток — отдельная последовательность выполнения внутри процесса.
- Производитель создаёт элементы, потребитель извлекает и обрабатывает их.
- Критическая секция изменяет общие данные и должна выполняться взаимно исключённо.
- Мьютекс позволяет только одному потоку одновременно изменять состояние буфера.
- Семафор хранит число доступных разрешений: `acquire()` уменьшает его или ждёт,
  `release()` увеличивает и позволяет продолжить одному из ожидающих.
- Условная переменная позволяет спать до возможного изменения состояния.
  Само условие хранится в общих данных и проверяется под мьютексом.
- Инвариант — утверждение, которое обязано оставаться истинным при работе программы.
- Барьер задерживает потоки, пока все участники не закончат текущую фазу.

## Кольцевой буфер и инварианты

Хранилище — массив из 5 ячеек. `head` указывает на следующее извлечение,
`tail` — на следующую вставку, `size` — число занятых ячеек.
Индексы изменяются по модулю 5: `(index + 1) % 5`.
Таким образом, после ячейки 4 снова используется ячейка 0.
`head == tail` возможно и при пустом, и при полном буфере; их различает `size`.

Под внешним мьютексом до и после каждой операции проверяются:

```text
0 <= size <= 5
0 <= head < 5
0 <= tail < 5
tail == (head + size) % 5
число занятых ячеек == size
занятые ячейки образуют правильный непрерывный участок кольца
```

Перед вставкой дополнительно проверяется `size < 5`, перед извлечением — `size > 0`.
Сам `RingBuffer` не захватывает мьютекс: его захватывает соответствующая оболочка.

Производители создают непересекающиеся последовательности:

```text
P0: 0, 3, 6, ..., 999   — 334 элемента
P1: 1, 4, 7, ..., 997   — 333 элемента
P2: 2, 5, 8, ..., 998   — 333 элемента
```

Суммарно создаются ровно 1000 элементов с ID 0..999.
Каждое потребление учитывается в `Counter` под отдельным мьютексом:
повторное потребление немедленно вызывает ошибку. После завершения
проверяется точное равенство `Counter(range(total))`, поэтому обнаруживаются
также пропуски и посторонние элементы.

Для завершения после `join()` всех производителей добавляются два служебных
маркера `STOP`, по одному на потребителя. Они идут через тот же FIFO-буфер,
не входят в 1000 элементов и учитываются отдельно: всего 1002 вставки и извлечения.
В конце буфер пуст. Распределение 1000 элементов между двумя потребителями
не обязано быть равным.

## Решение на семафорах

Начальное состояние:

```python
slots = threading.Semaphore(5)
items = threading.Semaphore(0)
mutex = threading.Lock()
```

Производитель: получить разрешение `slots`, под мьютексом вставить элемент,
затем выдать разрешение `items`.
Потребитель: получить разрешение `items`, под мьютексом извлечь элемент,
затем выдать разрешение `slots`.

Ожидание семафора происходит ДО захвата мьютекса: иначе можно заблокировать
поток, который должен освободить место или добавить элемент.
Семафоры регулируют доступное количество, мьютекс защищает массив и индексы.
Не следует утверждать, что внутреннее значение `items` в каждый момент равно
`size`: разрешение может быть уже зарезервировано потоком до захвата мьютекса.

## Решение на условной переменной

Одна `Condition` использует общий мьютекс.
Производитель ждёт в цикле, пока `size == 5`; потребитель — пока `size == 0`.
После изменения состояния выполняется `notify_all()`.
Выбран `notify_all`, потому что на одной условной переменной ждут разные роли:
нужно дать возможность перепроверить свои условия и производителям, и потребителям.

```python
with condition:
    while buffer_is_empty:
        condition.wait()
    take_item()
    condition.notify_all()
```

`wait()` атомарно ставит поток в ожидание и освобождает мьютекс.
Перед возвратом из `wait()` поток снова захватывает мьютекс.
`notify_all()` не освобождает мьютекс и не гарантирует, что условие стало истинным
для каждого разбуженного потока. Поэтому нужна повторная проверка `while`.
В основной программе ожидания имеют короткий тайм-аут для проверки отмены;
пробуждение по тайм-ауту также не означает наличие элемента.

## Барьер: 4 потока, 3 фазы

Собственный `ConditionBarrier` содержит счётчик прибывших и номер поколения.
Каждый поток завершает работу фазы и вызывает `wait()`.
Первые три потока ждут смены поколения в цикле.
Четвёртый сбрасывает счётчик, увеличивает поколение и выполняет `notify_all()`.

Номер поколения не позволяет смешать ожидающих текущей и следующей фазы.
При тайм-ауте барьер помечается сломанным, остальные ожидающие пробуждаются
с ошибкой. Готовый `threading.Barrier` не используется.

Под отдельным мьютексом аудита проверяется, что предыдущую фазу завершили
все 4 потока до старта следующей и что барьер не выпустил поток слишком рано.
В логе перед первым `start phase 2` должны присутствовать четыре `finish phase 1`.
Аналогично для перехода к третьей фазе.

## `if` вместо `while`: воспроизводимое нарушение

В `broken_wait.py --case if` оба потребителя видят пустой буфер и вызывают `wait`.
Производитель кладёт один элемент и вызывает `notify_all`.
Один потребитель захватывает мьютекс первым и забирает элемент.
Второй получает мьютекс позже, выходит из `wait`, не проверяет условие
и пытается извлечь элемент из пустого буфера: `UNDERFLOW`.
Для воспроизведения используются `Event`, а не надежда на случайный порядок потоков.

В `fixed_wait.py --case if` используется `while`. Второй потребитель повторно
засыпает; программа проверяет, что это произошло, и только затем добавляет
второй элемент. Оба элемента потребляются по одному разу, нарушений нет.

Терминологически это пробуждение с уже ложным условием (элемент забрал другой
поток), а не обязательно потерянное уведомление. Уведомление здесь получено.
Ложные пробуждения и тайм-ауты — дополнительные причины всегда использовать цикл.

## Настоящее потерянное пробуждение

В `broken_wait.py --case lost` намеренно разделены проверка и ожидание:

1. Потребитель проверяет пустоту и отпускает мьютекс.
2. Производитель добавляет элемент и вызывает `notify`, когда никто не ждёт.
3. Потребитель вызывает `wait`, опираясь на устаревшую проверку.
4. Нового уведомления нет: элемент лежит в буфере, потребитель спит.

Уведомления условной переменной не накапливаются как разрешения семафора.
Чтобы демонстрация не зависла, используется тайм-аут 0,2 с. Проверяется, что
`wait` завершился по тайм-ауту, хотя элемент уже присутствовал.

Исправление в `fixed_wait.py --case lost`: проверять предикат и вызывать
`wait` в одной критической секции, используя `while`. Производитель изменяет
данные и уведомляет под тем же мьютексом. Разрыва между проверкой и ожиданием нет.

## Контрольные вопросы

**1. Чем семафор со значением 1 отличается от мьютекса на практике?**

Семафор — счётчик разрешений; `Semaphore(1)` имеет начальное значение 1,
но обычный семафор допускает увеличение выше 1 при лишних `release`.
`BoundedSemaphore(1)` обнаруживает такое превышение. Бинарный семафор
может обеспечивать взаимное исключение при правильном использовании,
а также служить сигналом между потоками: один захватил, другой освободил.
Мьютекс предназначен для защиты критической секции; многие API связывают его
с владельцем и требуют освобождения тем же потоком.
Особенность Python: примитивный `threading.Lock` допускает освобождение другим
потоком; `RLock` учитывает владельца и повторные захваты. Поэтому утверждение
«все мьютексы всегда проверяют владельца» для Python было бы неточным.

**2. Почему условную переменную нельзя использовать без мьютекса?**

Уведомление не хранит состояние условия. Без общего мьютекса между проверкой
условия и входом в ожидание другой поток может изменить данные и отправить
уведомление, которое будет потеряно. Мьютекс защищает предикат и позволяет
атомарно перейти от проверки к ожиданию; `wait` освобождает его на время сна
и захватывает перед возвратом. В Python у `Condition` всегда есть связанная
блокировка, в том числе автоматически созданная, если её не передали явно.
Методы `wait` и `notify` вызываются при удержании этой блокировки.
